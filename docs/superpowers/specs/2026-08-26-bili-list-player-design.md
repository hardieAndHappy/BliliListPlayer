# BiliListPlayer 项目需求文档

## 1. 文档信息

- 项目名称：BiliListPlayer
- 文档类型：Windows PC 桌面端产品需求与技术设计（MVP）
- 日期：2026-08-26
- 目标平台：Windows 10/11（PC 桌面端）
- 交付形式：无需安装 Node.js/npm 的 Windows `.exe` 应用或安装包
- 技术框架：Tauri 2.x（桌面壳）+ HTML/CSS/React/TypeScript（内嵌界面）+ Rust（本地后端）
- 播放方式：Tauri 内嵌 WebView 中的 Bilibili 网页在线播放

### 1.1 运行与发布边界

- npm、Node.js 和 Vite 仅用于开发、测试和构建阶段，不属于用户运行时依赖。
- 发布构建将 HTML、CSS、JavaScript 和静态资源编译并打包进 Tauri 应用；用户启动 `.exe` 时不执行 `npm` 命令，也不启动 Node.js 服务。
- Rust 后端随 Tauri 应用一同编译进桌面程序，负责本地文件、解析、播放桥接和系统能力；前端通过 Tauri `invoke/events` 与 Rust 通信。
- 发布物必须包含 WebView2 运行条件检查和明确提示；应用本身不要求用户准备 npm、Node.js、Rust 或独立后端服务。
- Windows 构建产物至少包括一个可直接运行的 `.exe`；如提供安装包，安装包只负责安装应用及其资源，不额外安装开发工具链。

## 2. 背景与目标

Bilibili 的部分列表页面（例如用户提供的 `/list/12853451`）适合浏览和播放，但缺少便捷的本地编辑能力。用户无法稳定地维护自己的播放顺序，也难以在下次打开时直接继续收听。

BiliListPlayer 提供一个轻量桌面工具：用户在应用内正常登录 Bilibili，导入列表后即可本地增删、排序、循环或随机播放；应用把列表、编辑历史和播放记录保存在 Windows 用户可写的应用数据目录，方便下次启动时恢复，不需要重复打开 Bilibili 列表页面。

## 3. 产品范围

### 3.1 MVP 包含

1. 在内嵌 WebView 中打开 Bilibili，并由用户完成正常网页登录。
2. 粘贴 Bilibili 列表 URL，解析列表项目并导入本地队列。
3. 保存多个 Bilibili 列表来源，支持在新旧导入之间切换、重命名、归档和删除。
4. 对当前本地队列进行新增、删除、批量删除、排序、恢复最近删除和清空。
5. 提供上一首、下一首、暂停/继续、单曲循环、列表循环、随机播放。
6. 保存并恢复当前列表、播放模式、当前项目和最近播放位置。
7. 记录所有列表编辑事件和播放事件，支持查看与筛选。
8. 对网络异常、登录失效、项目失效和数据文件损坏提供可操作提示。

### 3.2 明确不包含

- 不下载、转码、缓存或导出音频/视频文件。
- 不绕过 Bilibili 登录、风控、访问控制或版权限制。
- 不读取 Chrome 或其他浏览器的 Cookie，不提供 Cookie 导入。
- 不保存账号密码；仅使用 WebView 自身的站点会话数据。
- MVP 不提供云同步、多设备同步、账号体系或社交功能。

## 4. 用户故事与验收标准

### 4.1 主要用户故事

- 作为用户，我可以粘贴一个 Bilibili 列表 URL，把视频加入自己的本地播放列表。
- 作为用户，我可以保存多个 Bilibili 列表 URL，并在新导入和旧导入之间切换管理。
- 作为用户，我可以删除不想听的项目、调整顺序，并在误删后恢复。
- 作为用户，我可以选择循环或随机播放，并在应用重启后保持选择。
- 作为用户，我可以查看最近听过的项目，下次直接继续播放。
- 作为用户，我可以追溯列表发生过哪些增删和排序变化。

### 4.2 MVP 验收标准

- 重启应用后，列表内容、顺序、播放模式、当前项目和最近播放位置保持一致。
- 重启应用后，所有未归档的本地列表来源、名称、来源 URL、导入版本和各自播放上下文保持一致；启动时恢复上次激活来源。
- 每次新增、删除、批量删除、移动、恢复、清空均写入可追溯的历史事件，事件包含时间、类型、项目快照和来源列表。
- 播放开始、完成、跳过、失败均写入播放历史，并累计项目播放次数和最近播放时间。
- 随机模式在同一轮次内不重复已播放项目；列表只有一个项目时允许重复。
- 播放控制由 Bilibili WebView 页面完成，应用不产生媒体下载文件。
- 登录过期、网络断开或项目失效时显示原因、重试入口和跳过入口。
- 单次文件写入失败不能破坏上一次有效数据；下次启动可以恢复或提示恢复备份。

## 5. 功能需求

### 5.1 登录与列表导入

- 首次启动展示 Bilibili 登录提示和“打开登录页”按钮。
- WebView 保留自己的 Cookie/LocalStorage 会话；用户退出应用后再次启动可继续使用有效会话。
- 用户可粘贴 `https://www.bilibili.com/list/<id>` 或兼容的 Bilibili 列表 URL。
- 列表 URL 可能是网站生成的临时列表，不能把来源页 URL 当作可播放项目；导入器必须读取列表页中指向具体视频的页面链接，提取并规范化真实项目 URL（如 `https://www.bilibili.com/video/BV...`）及 BV/AV 标识，再组装成本地播放列表。
- 项目 URL 提取仅限 Bilibili 页面层链接和公开元数据；禁止提取 `playurl`、音视频流地址、签名参数或执行下载。
- 每次导入都可保存为一个本地列表来源；用户可以填写名称，之后从列表来源管理页切换到任意已保存的导入。
- 对已保存的相同来源 URL，导入时由用户选择“更新现有列表”或“另存为新列表”，不得静默覆盖旧导入。
- 列表来源支持重命名、归档、恢复和删除；删除来源前必须确认，归档来源保留其项目、播放进度和历史记录但不出现在默认播放入口。
- 解析结果至少包含：标题、BV/AV 标识、页面 URL、封面 URL、UP 主、时长（可获取时）。
- 导入前展示预览，支持全选/取消选择；按 BV/AV 标识去重。
- 无法解析或已失效的项目保留在结果中并标记状态，不阻塞其他项目导入。

### 5.2 本地列表编辑

- 支持单个新增、批量新增、删除、批量删除、拖拽排序。
- 删除前提供确认；清空操作必须二次确认。
- 提供“恢复最近删除”操作，恢复时保持原顺序信息（可恢复时）。
- 列表项目状态至少包括：可播放、待验证、已失效、已删除。
- 所有变更先更新内存状态，再以原子替换方式写入磁盘并追加历史事件。

### 5.3 播放控制

- 控件：播放/暂停、上一项、下一项、进度显示、音量（由网页播放器支持时）、播放模式。
- 播放模式：顺序播放、列表循环、单曲循环、随机播放。
- 随机播放维护当前轮次队列；切换模式或列表发生结构性变化时重新生成轮次。
- 播放结束由 WebView 页面事件触发下一项；事件不可用时提供手动下一项。
- 记录播放开始、播放完成（播放进度达到配置阈值）、跳过和失败。

### 5.4 历史与继续收听

- 编辑历史页面支持按时间、操作类型和项目筛选。
- 播放历史页面支持按最近播放时间和播放次数排序。
- 历史事件为追加写入，不允许直接修改；恢复操作生成新的恢复事件。
- 启动时恢复上次活动列表和播放上下文，并提供“从上次位置继续”按钮。
- 历史文件可按大小轮转，默认保留最近 10,000 条事件；轮转不影响当前列表。

### 5.5 Web 界面视觉与交互风格

- 整体采用接近 Bilibili 网页端的内容消费风格：浅色背景、卡片化内容区、圆角控件、清晰的播放主区域和紧凑的列表信息层级。
- 主色使用 Bilibili 风格的粉色作为强调色（默认 `#FB7299` 或主题配置值），用于主按钮、当前播放状态和进度条；蓝色（默认 `#00AEEC`）用于链接及次要信息；危险操作使用独立的红色，不与主色混淆。
- 页面结构参考“顶部导航 + 左侧功能栏 + 中央内容区 + 底部播放控制栏”：顶部放置应用名称、列表导入、登录状态和设置；左侧放置已保存列表来源、当前列表、最近播放和编辑历史入口；中央展示可排序播放队列；底部固定播放控制栏。
- 已保存列表来源展示名称、来源 URL、项目数量、最近导入时间和归档状态；切换来源前提示未保存编辑或自动完成保存。
- 列表项目采用 Bilibili 风格的信息密度：封面缩略图、标题、UP 主、时长、播放状态和更多操作；当前项目使用浅色高亮、播放图标和主色边框标识。
- 播放区支持在“应用内 WebView 播放”与“列表管理优先”两种布局间切换；窄窗口下自动折叠侧栏和非关键字段，保证队列与控制栏可用。
- 交互反馈遵循网页端习惯：按钮悬停/按下状态、Toast 成功提示、确认弹窗、骨架屏加载和空状态引导；键盘支持空格播放/暂停、方向键切换项目、`Delete` 删除选中项。
- 字体、图标和间距保持统一设计令牌；优先使用开源图标和自有组件，不直接复制 Bilibili 的商标、专有图片或页面代码。

## 6. 数据与文件规范

数据文件默认位于 Windows 用户可写的应用数据目录，不与 `.exe` 同目录绑定；应用提供“打开数据目录”和“更换数据目录”入口。安装目录无写权限时不影响正常使用：

```text
data/
  playlists.json          # 多个本地列表来源、项目及各自播放上下文
  edit-history.jsonl      # 列表编辑事件
  playback-history.jsonl  # 播放事件
  backups/                 # 最近一次成功保存的备份
```

`playlists.json` 至少包含当前激活来源和多个本地列表来源：

```json
{
  "version": 1,
  "updatedAt": "2026-08-26T00:00:00Z",
  "activePlaylistId": "local-001",
  "playlists": [{
    "id": "local-001",
    "name": "通勤歌单（8月）",
    "sourceUrl": "https://www.bilibili.com/list/12853451",
    "status": "active",
    "createdAt": "2026-08-26T00:00:00Z",
    "updatedAt": "2026-08-26T00:00:00Z",
    "items": [{
      "id": "BV...",
      "title": "...",
      "url": "https://www.bilibili.com/video/BV...",
      "coverUrl": "...",
      "author": "...",
      "status": "playable",
      "position": 0,
      "lastPositionSeconds": 0,
      "playCount": 0,
      "lastPlayedAt": null
    }],
    "playback": {
      "mode": "list-loop",
      "currentItemId": "BV...",
      "currentPositionSeconds": 0,
      "randomSeed": null
    }
  }]
}
```

编辑和播放历史每行一个 JSON 事件，至少包含 `eventId`、`timestamp`、`type`、`playlistId`（适用时）、`itemId`（适用时）、`sourcePlaylistUrl`（适用时）和 `snapshot`（变更相关时）。

## 7. 技术架构

```text
HTML/CSS/React/TypeScript UI（构建后随 EXE 分发）
   ├─ 列表编辑状态与播放模式状态
   ├─ WebView 播放桥接（页面事件/控制命令）
   └─ 历史查看与错误提示
          │ Tauri invoke/events
Rust Core
   ├─ Bilibili 列表解析适配器
   ├─ 原子文件存储与备份恢复
   ├─ 编辑/播放事件追加器
   └─ 播放上下文与随机队列服务
          │
Windows 应用数据目录 data/ 文件
```

- 前端只通过 Tauri 命令读写持久化数据，不直接访问文件系统。
- Rust 存储层采用“写临时文件 → flush → 原子替换 → 更新备份”的流程；JSONL 事件追加失败时显示错误并保留内存状态待重试。
- 解析器与 UI 解耦，以结构化项目 DTO 交互，页面结构变化只影响解析适配器。
- 列表解析适配器区分“来源列表 URL”和“项目视频 URL”：先解析临时/持久列表页面中的视频链接，再对项目页面元数据进行补全；任一项目解析失败只标记该项目，不丢弃整个来源。
- WebView 桥接只发送播放控制和受限页面事件，不提取媒体地址。

### 7.1 构建与发布流程

1. 开发机使用 Node.js/npm 安装依赖并运行前端检查、单元测试和 Vite 构建；这些步骤只发生在开发/CI 环境。
2. Tauri 构建命令将构建后的前端静态目录嵌入应用，并编译 Rust 后端生成 Windows 目标程序。
3. 发布前验证最终 `.exe` 在未安装 Node.js/npm 的干净 Windows 环境中可以启动、显示界面、读写数据并完成基本播放流程。
4. 发布包不得依赖项目目录、`node_modules`、npm 缓存、Vite 开发服务器或外部 Rust 服务。
5. 只编译构建exe，不做安装包

## 8. 错误处理与安全

- 未登录：引导打开登录页，暂停自动导入和自动播放。
- 登录过期/风控：保留当前列表，提示用户在 WebView 中重新验证。
- 网络错误：区分加载失败与播放失败，提供重试、跳过和稍后处理。
- 数据损坏：将原文件改名为带时间戳的 `.corrupt` 备份，尝试读取最近成功备份；无备份时使用空列表并提示。
- 路径无权限或磁盘空间不足：阻止覆盖旧文件，显示数据目录和处理建议。
- 所有外部 URL 仅允许 `https://www.bilibili.com/` 及必要的 Bilibili CDN 页面资源；拒绝任意脚本注入和外部重定向。

## 9. 测试要求

- 单元测试：URL 解析、项目去重、随机队列、播放模式切换、事件序列化、损坏文件恢复。
- 集成测试：列表编辑后文件内容与历史事件一致；原子保存失败时旧数据可读。
- WebView 手工测试：登录、会话恢复、播放结束事件、登录过期、失效项目和网络断开。
- 回归场景：至少 20 个项目连续播放，顺序/循环/单曲循环/随机四种模式各验证一次。

## 10. 审计要求

### 10.1 安全审计

- **会话边界**：确认只使用 Tauri WebView 自身的 Cookie/LocalStorage；代码库不得出现读取 Chrome Cookie 数据库、DPAPI 解密或导出 Cookie 的实现。
- **媒体边界**：搜索依赖、Rust 命令和前端代码中的 `download`、媒体 URL 提取、文件写入调用，确认播放链路只加载 Bilibili 页面。
- **外链边界**：验证导航白名单仅允许 Bilibili 页面及必要资源域名；阻止任意外部跳转、脚本注入和危险协议。
- **命令边界**：逐项审查 Tauri `invoke` 命令的输入校验、错误返回和权限声明，确保前端不能传入任意文件路径。
- **敏感数据**：确认日志、崩溃报告和历史文件不包含密码、Cookie 值、Authorization Header 或完整个人隐私信息。
- **依赖审计**：发布前执行 `npm audit` 与 `cargo audit`；高危漏洞必须阻断发布或记录经批准的风险接受。

### 10.2 数据可靠性审计

- **原子性**：检查保存流程是否先写临时文件并成功 flush，再替换主文件；模拟中断后主文件必须可解析。
- **备份恢复**：验证损坏文件会保留 `.corrupt` 副本，且最近一次成功备份可恢复。
- **事件一致性**：列表状态变更成功后才追加事件；失败操作不得伪造成功事件。
- **版本迁移**：为 `version` 字段准备未知版本拒绝策略和已支持版本迁移测试。
- **轮转完整性**：历史轮转后事件数量、最后一条事件和主列表引用仍然一致。

### 10.3 体验与合规审计

- 验证首次使用、登录过期、网络失败、空列表和无权限目录均有明确下一步操作。
- 验证 Bilibili 风格仅作为视觉参考，不复制其商标、专有素材、页面代码或未授权接口。
- 验证应用说明中明确“在线播放、不下载、不导出媒体”，并提供数据目录清理说明。
- 审计结论记录在 `docs/audits/YYYY-MM-DD-audit.md`，包含版本、环境、执行人、证据路径、风险等级和整改状态。

## 11. 非功能要求

- 启动后 2 秒内显示本地列表（不等待网络）。
- 本地编辑操作界面反馈时间目标小于 100 ms。
- 历史文件采用追加写入，异常退出后不影响主列表文件。
- Windows 10/11 优先支持；架构设计保留 macOS/Linux 适配空间。
- 应用不上传用户列表、播放历史、Cookie 或账号信息。
- 最终用户运行应用不需要安装 Node.js、npm、Rust、Vite 或其他开发工具链。
